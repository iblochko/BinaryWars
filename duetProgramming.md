## «Парное программирование»

**Тема:** Разработка пошаговой стратегии на движке Godot 4

---

## 1. Какую задачу реализовывали?

Мы разрабатывали базовую механику пошаговой стратегии на движке Godot 4. Проект состоит из пяти скриптов, которые реализовывались совместно в паре.

**Реализованные модули:**

- **`Unit.gd`** — базовый класс юнита `BaseUnit`: движение по сетке, визуальное выделение при выборе, управление количеством ходов, выравнивание спрайта по центру клетки, регистрация в группе `units`.
- **`Onerrior.gd`** — конкретный класс воина, наследующий `BaseUnit`: параметры здоровья (100), атаки (10), брони (5), дальности атаки (1). Логика получения урона с учётом брони, атака по цели, смерть с удалением с карты.
- **`MapManager.gd`** — менеджер карты: загрузка тайлов из `TileMap`, BFS-алгоритм поиска пути, валидация перемещений, подсветка доступных клеток, словарь `units_on_map` для отслеживания позиций юнитов.
- **`CameraManager.gd`** — управление камерой: масштабирование колёсиком мыши с ограничением (0.1–3.0), плавное перемещение по WASD/стрелкам через `_velocity.move_toward()`.
- **`node.gd` (UnitTestRunner)** — скрипт unit-тестов: проверка логики урона воина и логики поиска пути `MapManager`, демонстрирующий стиль «Пинг-понг».

---

## 2. Какой стиль показался более приемлемым? Почему?

Мы пробовали оба стиля: **«Ведущий-ведомый»** и **«Пинг-понг»**. Наиболее эффективным оказался **«Пинг-понг»** при написании игровой логики и тестов.

### Стиль «Пинг-понг» — основной

Применялся при реализации боевой механики и тестировании. Алгоритм работы:

1. **Партнёр А** пишет тест с ожидаемым результатом. Например: воин с бронёй 5 должен получить 0 урона от атаки силой 3.
2. **Партнёр Б** реализует функцию `take_damage()` в `Onerrior.gd` так, чтобы тест прошёл.
3. Роли меняются: Партнёр Б пишет тест на `find_path()`, Партнёр А реализует BFS в `MapManager.gd`.

Ключевое преимущество: мы сразу заметили и исправили ошибку, при которой здоровье юнита уходило в отрицательные значения. Тест **«Смерть юнита: здоровье не уходит в минус»** выловил её ещё до первого запуска игры.

### Стиль «Ведущий-ведомый» — дополнительный

Использовался при настройке сцены в редакторе Godot: расстановка `TileMap`, `Camera2D`, настройка `@export`-переменных и сигналов. Партнёр, лучше знакомый с интерфейсом редактора, выступал ведущим и объяснял, второй наблюдал и задавал вопросы.

---

## 3. Что получилось? Положительные впечатления.

### Качество кода и обнаружение ошибок

Тесты немедленно выявили реальную ошибку: без строки `max(0, health - actual_damage)` здоровье уходило в минус. Тест на путь к самому себе подтвердил, что `find_path()` корректно возвращает массив из одной клетки.

### Архитектурные решения

В паре удалось договориться о чёткой структуре: `BaseUnit` как базовый класс, наследование через `extends`, хранение юнитов в словаре `units_on_map`. Это оказалось намного чище первоначальной идеи с массивом.

### Обмен знаниями

- Один партнёр объяснил другому работу с группами Godot (`add_to_group` / `get_nodes_in_group`) и сигналами (`signal` / `emit_signal`).
- Совместно разобрались с BFS-алгоритмом и придумали параметр `ignore_unit`, чтобы юнит не блокировал сам себя при подсветке доступных клеток.
- Обсудили и реализовали плавное движение камеры через `_velocity.move_toward()` вместо телепортации позиции.

### Дисциплина и концентрация

Работа в паре создавала естественную ответственность: сложнее отвлечься, когда партнёр ждёт следующего шага. Это особенно помогло при отладке алгоритма поиска пути.

---

## 4. Что не получилось? Как можно это поправить?

| Проблема | Решение |
|---|---|
| Тесты `MapManager` требуют запущенной сцены с `TileMap`, поэтому их нельзя запустить изолированно | Выделить логику пути в отдельный статический класс `PathFinder` без зависимости от `TileMap` — тогда тест запускается без сцены |
| В стиле «Пинг-понг» написание теста иногда занимало больше времени, чем реализация — особенно при проверке движения юнита по пути | Договариваться о масштабе теста заранее: проверять только возвращаемое значение функции, а не визуальный результат на экране |
| Редактирование одного скрипта двумя людьми без контроля версий приводило к путанице | Использовать Git: один работает в ветке — второй ревьюит. Делать коммит после каждого пройденного теста |

---

## 5. Будете ли использовать ПП для других задач? Каких?

**Да, будем.** Опыт показал, что парное программирование оправдывает себя там, где ошибка дорого обходится — в игровом проекте это ошибки в формулах баланса, алгоритмах и архитектуре классов.

**Задачи, для которых будем использовать ПП:**
- Реализация ИИ противников — алгоритм принятия решений сложный, логические ошибки в нём сложно заметить в одиночку.
- Рефакторинг: выделение UI в отдельную сцену, разбиение `MapManager` на более мелкие классы.
- Балансировка характеристик юнитов — пока один меняет цифры, второй сразу пишет тест и проверяет сценарии боя.

**Задачи, для которых ПП не нужен:**
- Настройка анимаций и визуальных эффектов — работа в редакторе, не требующая обсуждения логики.
- Вёрстка UI-сцен — механическая расстановка элементов интерфейса.

## Приложение: Ключевые фрагменты кода

### Логика урона с бронёй — `Onerrior.gd`

```gdscript
func take_damage(amount: int):
    var actual_damage = max(0, amount - defense)
    health = max(0, health - actual_damage)
    print("🛡️ Воин получил ", actual_damage, " урона. Осталось: ", health)
    if health <= 0:
        die()
```

### Тесты для `take_damage` — `node.gd`

```gdscript
func test_warrior_take_damage():
    var warrior = load("res://scripts/units/Onerrior.gd").new()
    warrior.health = 100
    warrior.defense = 5

    # Сценарий 1: урон меньше брони → здоровье не меняется
    warrior.take_damage(3)
    assert_equal(warrior.health, 100, "Урон меньше брони (3 < 5)")

    # Сценарий 2: урон больше брони → здоровье 100 - (10-5) = 95
    warrior.health = 100
    warrior.take_damage(10)
    assert_equal(warrior.health, 95, "Урон больше брони (10 - 5 = 5)")

    # Сценарий 3: смерть → здоровье не уходит в минус
    warrior.health = 5
    warrior.defense = 0
    warrior.take_damage(10)
    assert_equal(warrior.health, 0, "Смерть: здоровье не уходит в минус")
```

### Тесты для `find_path` — `node.gd`

```gdscript
func test_map_manager_logic():
    var map_mgr = get_tree().get_first_node_in_group("map_manager")
    if map_mgr:
        # Путь к самому себе — массив из 1 клетки
        var path = map_mgr.find_path(Vector2i(0,0), Vector2i(0,0), 5, true)
        assert_equal(path.size(), 1, "Путь к самому себе (размер 1)")

        # Путь на соседнюю клетку — массив из 2 клеток
        path = map_mgr.find_path(Vector2i(0,0), Vector2i(0,1), 5, true)
        assert_equal(path.size(), 2, "Путь на соседнюю клетку (размер 2)")

        # Путь по диагонали (2 шага) — массив из 3 клеток
        path = map_mgr.find_path(Vector2i(0,0), Vector2i(1,1), 5, true)
        assert_equal(path.size(), 3, "Путь по диагонали (размер 3)")
```

### BFS-алгоритм поиска пути — `MapManager.gd`

```gdscript
func find_path(from_cell: Vector2i, to_cell: Vector2i,
               max_range: int, ignore_unit: bool = false) -> Array[Vector2i]:
    if from_cell == to_cell:
        return [from_cell]
    if not is_passable(to_cell):
        return []

    var queue: Array[Vector2i] = [from_cell]
    var came_from: Dictionary = { from_cell: null }
    var visited: Dictionary  = { from_cell: 0 }

    while queue.size() > 0:
        var current = queue.pop_front()
        if current == to_cell: break
        if visited[current] >= max_range: continue

        for neighbor in get_neighbors(current):
            if not visited.has(neighbor) and is_passable(neighbor):
                if not ignore_unit and is_cell_occupied(neighbor):
                    continue
                queue.append(neighbor)
                visited[neighbor] = visited[current] + 1
                came_from[neighbor] = current

    # Восстановление пути
    var path: Array[Vector2i] = []
    var cur = to_cell
    while cur != null:
        path.append(cur)
        cur = came_from.get(cur)
    path.reverse()
    return path
```
